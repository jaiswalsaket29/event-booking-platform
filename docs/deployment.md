# Deployment

The backend ships as one Docker image (`backend/Dockerfile`) that runs with the `prod` profile and reads all configuration from environment variables. It needs PostgreSQL 16 and Redis 7. Any platform that builds a Dockerfile works; the repo includes a [Render](https://render.com) Blueprint (`render.yaml`) that creates all three pieces.

> Status: the Blueprint and image are ready, and the image has been run locally in prod mode against Postgres and Redis. Nothing has been deployed yet; that needs a hosting account. The Blueprint hasn't been through Render's validator.

## Environment variables

| Variable | Required | Notes |
|---|---|---|
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | yes | PostgreSQL connection (`DB_PORT` defaults to 5432) |
| `DB_URL_PARAMS` | no | Appended to the JDBC URL, e.g. `?sslmode=require` for an external database |
| `REDIS_URL` | yes | `redis://` or `rediss://` (TLS), with credentials if any |
| `JWT_SECRET` | yes | Random, at least 32 bytes. Startup fails with the published dev/placeholder values |
| `PAYMENT_WEBHOOK_SECRET` | yes | Random, at least 32 bytes. Same check |
| `ADMIN_PASSWORD` | yes | Becomes the password of `admin@eventbooking.dev` at startup (min 12 chars). Startup fails while the dev password is still in use |
| `CORS_ALLOWED_ORIGINS` | yes | Comma-separated frontend origins, e.g. `https://events.example.com,https://admin.example.com` |
| `FRONTEND_USER_URL` | yes | Base URL of the user site, used in email links |
| `PORT` | no | Set by most platforms; defaults to 8080 |
| `SEED_DEMO_DATA` | no | `true` seeds the fictional demo catalog into an empty database (default `false`) |
| `API_DOCS_ENABLED` | no | `true` exposes Swagger UI and the OpenAPI spec publicly (default `false`) |
| `RATE_LIMIT_ENABLED` | no | Default `true` |
| `REDIS_CONFIGURE_KEYSPACE_NOTIFICATIONS` | no | Default `false`: managed Redis usually forbids `CONFIG SET`. Without expiry events the sweeper releases expired holds within about a minute |
| `SPRING_MAIL_HOST`, `SPRING_MAIL_PORT`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD`, `MAIL_FROM` | for a usable demo | SMTP for verification, reset and ticket emails. **Without it, emails are only logged and new users can't verify their email, so they can't book.** Don't set `SPRING_MAIL_HOST` to an empty value |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET`, `R2_PUBLIC_BASE_URL` | no | Direct image upload to Cloudflare R2; without them admins add images by URL |

The container runs as a non-root user and sizes its heap from the memory limit (`-XX:MaxRAMPercentage=75`).

## Render (Blueprint)

1. Push `main` to GitHub.
2. Render dashboard → **New** → **Blueprint** → select the repository. Render reads `render.yaml` and proposes:
   - `eventbooking-api`: web service built from `backend/Dockerfile`, health check `/actuator/health/readiness`;
   - `eventbooking-db`: PostgreSQL 16;
   - `eventbooking-redis`: Key Value (Redis-compatible), internal only, `noeviction`.
3. Fill in the prompted values: `ADMIN_PASSWORD` (store it in a password manager), `CORS_ALLOWED_ORIGINS` and `FRONTEND_USER_URL` (use the frontend URLs once they exist; until then, any placeholder `https://` URL works). `JWT_SECRET` and `PAYMENT_WEBHOOK_SECRET` are generated by Render.
4. For working signups, add the SMTP variables to `eventbooking-api` under **Environment** (any SMTP provider with a free tier).
5. Deploy. The first start runs the Flyway migrations and seeds the demo catalog; the service goes live once readiness is UP.

Check it:

```bash
curl https://<your-service>.onrender.com/actuator/health
curl "https://<your-service>.onrender.com/api/v1/events?size=3"
```

Free-plan limits: the web service sleeps after about 15 minutes without traffic (the first request after that takes a while), and a free Postgres database expires after 30 days unless upgraded. Hold timers keep working across a sleep because the sweeper releases stale holds on wake-up.

## Other platforms

Railway, Fly.io and similar hosts can build `backend/Dockerfile` directly (build context `backend/`). Create PostgreSQL 16 and Redis, then set the variables above. Point the platform's health check at `/actuator/health/readiness` (liveness: `/actuator/health/liveness`).

## Running the production image locally

```bash
cd backend
docker build -t eventbooking-backend .
docker compose up -d
docker exec backend-postgres-1 createdb -U eventbooking eb_prod
docker run --rm --network backend_default -p 8098:8080 \
  -e DB_HOST=postgres -e DB_NAME=eb_prod -e DB_USER=eventbooking -e DB_PASSWORD=devpassword \
  -e REDIS_URL=redis://redis:6379 \
  -e JWT_SECRET=<32+ random chars> -e PAYMENT_WEBHOOK_SECRET=<32+ random chars> \
  -e ADMIN_PASSWORD=<12+ chars> \
  -e CORS_ALLOWED_ORIGINS=http://localhost:5173 -e FRONTEND_USER_URL=http://localhost:5173 \
  -e SEED_DEMO_DATA=true eventbooking-backend
```

Use a separate database (`eb_prod` above) so `ADMIN_PASSWORD` doesn't replace the dev admin password in your dev database.
